## Context

Greenfield repository. Motivation in proposal.md, behavior in `specs/*/spec.md`. Constraints that shape the architecture:

- No API keys. Inference must come from the engineer's ChatGPT or Claude subscription, and the owner wants the approach omp (oh-my-pi) uses: the application implements the providers' OAuth flows itself, keeps refresh tokens in its own vault, refreshes and rotates accounts, and calls the provider APIs directly. This is the same posture as omp and OpenCode.
- Policy exposure: Anthropic's terms state that third-party developers may not offer Claude.ai login or route requests through Free/Pro/Max credentials, and that Anthropic may enforce without notice. OpenAI documents the ChatGPT sign-in for Codex surfaces only. BrainBench is self-hosted, so the account at risk is the engineer's own; the design makes each provider individually enableable, documents the exposure in the README, and keeps the provider layer isolated so a provider can be removed or swapped for an API-key or local model without touching agents.
- Subscription endpoints expose chat only; no embeddings. Embeddings run locally.
- Self-hosted, single-tenant: one engineer per instance. Web UI is the primary surface.
- Manim scripts are untrusted generated code and must run in a sandbox. Interactive figures come from the Anatomy agent skill (`wheresryan22/anatomy`, MIT): a `SKILL.md` workflow plus a zero-dependency Node kit and headless-Chromium checks. With in-house inference the skill runs under BrainBench's own Strands agent with file and Node tools confined to a sandbox; no vendor CLI is involved.
- The tutor needs token streaming from the provider into the browser; direct API access makes that native.

## Goals / Non-Goals

**Goals:**
- A provider layer structured like omp's: a declarative registry, an encrypted credential vault, OAuth engines (authorization-code with PKCE, device-code), a single-flight refresher, usage windows and rate-limit blocks per account, account ranking, and wire transports, so adding a provider is a registry entry plus at most a transport hook.
- One `docker compose up` brings up the whole stack; the only host prerequisite is Docker.
- Every agent step produces schema-validated JSON so downstream code never parses prose; tool calling is native.
- Untrusted generated code (Manim scripts, Anatomy builds) runs with no network, bounded CPU time, and a workspace-only mount.

**Non-Goals:**
- Multi-user accounts, SSO, or per-user billing.
- A remote auth broker or gateway (omp's `auth-broker` / `auth-gateway`); the vault is local to the instance.
- API-key logins. The registry grammar leaves room for an `api-key` login kind, but none ships.
- GPU rendering, streaming video transcoding, or CDN delivery.
- Mobile UI.

## Decisions

### D1. Monorepo layout and languages
One repository, one commit history, one CI, with workspace tooling at the root:
- Root `pyproject.toml` declares a `uv` workspace (`[tool.uv.workspace] members = ["apps/api", "packages/providers", "packages/agents"]`) and the shared `ruff`, `mypy`, and `pytest` configuration; a single `uv.lock` lives at the root and `apps/api` depends on `packages/providers` and `packages/agents` as workspace sources. `uv sync` at the root installs everything; `uv run --package brainbench-api pytest` targets one member.
- Root `package.json` declares Bun workspaces (`"workspaces": ["apps/web"]`) with a single `bun.lock`; future web packages join the same workspace.
- Root `justfile` is the task runner (`just dev`, `just test`, `just lint`, `just build`, `just smoke`) and the only thing CI calls; `.github/workflows/ci.yml` runs Python and web jobs from the root. Docker builds use the repository root as context so `packages/*` are available to `Dockerfile.app`.
- `apps/api`: Python 3.15 managed by `uv` (`.python-version` at the root, `uv python install`, `uv sync`, `uv run`), FastAPI, SQLAlchemy 2 (async), Alembic, Pydantic v2 and pydantic-settings. Layout follows `BACKEND_GOOD_PRACTICES.md`: `app/api/v1/` (thin routers), `app/core/` (config, logging), `app/db/` (engine, session, ORM schema), `app/models/` (request/response contracts), `app/services/` (business logic), `app/jobs/` (job handlers run by the worker), `tests/` mirroring `app/`. Two entrypoints in the same package: `app/main.py` (API) and `app/worker.py` (job runner that polls the jobs table).
- Lazy imports (PEP 810, Python 3.15): heavy or path-specific dependencies are declared at module top level with `lazy import` / `lazy from ... import` so the API process never loads `fastembed`, `pymupdf`, `trafilatura`, or `docker`, and the worker loads each only when a job of that type runs. Eager imports are mandatory for anything with import-time side effects or registration: `app.core.config`, `app.core.logging`, `app.db.schema` (ORM mapper registry), routers included in `app/main.py`, Alembic `env.py`. The global `-X lazy_imports=all` mode is never used; CI runs the suite once normally and once with `PYTHON_LAZY_IMPORTS=none` to surface broken deferred imports eagerly. Full rules in `BACKEND_GOOD_PRACTICES.md`.
- `apps/web`: React 19 + MUI (Material UI) + TypeScript, run entirely on Bun: Bun is the package manager (`bun install`, committed `bun.lock`), bundler (HTML imports, `bun build`), dev server with HMR (`bun --hot server.ts`), production server (`Bun.serve`), and test runner (`bun test`). `server.ts` registers `/api/*` and `/events` as explicit proxy routes to FastAPI and `/*` as the SPA fallback (Bun matches explicit routes before the wildcard; putting the proxy only in the `fetch` fallback would never run because `/*` already matches), so the browser stays same-origin and the session cookie just works. Client routing with React Router (library mode), server state with TanStack Query, live updates via `EventSource`, figures embedded in a sandboxed `<iframe>`, tutor sidebar as a persistent MUI `Drawer`. Conventions in `FRONTEND_GOOD_PRACTICES.md`.
- `packages/providers`: the omp-style provider layer (D2): registry, vault, OAuth engines, refresher, usage, account selection, wire transports, and the Strands `Model` adapters on top. Pure Python, no FastAPI; consumed by `packages/agents` and `apps/api`.
- `packages/agents`: Strands Agents SDK (`strands-agents` on PyPI, imported as `strands`). One `Agent` factory per task class with its system prompt and Pydantic output model, the `@tool` functions agents may call, the sandboxed file and Node tools for figure building, and hooks for usage accounting. Consumed by `apps/api/app/jobs` and `app/services/tutor.py`; never imports from `app`.
- `infra/`: `docker-compose.yml` at the repository root (so `docker compose up` works from a fresh clone with no flags), `infra/Dockerfile.app` (python 3.15-slim, used by `init`, `api`, and `worker`), `infra/Dockerfile.web`, `infra/Dockerfile.manim`, `infra/Dockerfile.anatomy` (Node 20 + Chromium, no npm packages, used as the figure sandbox), Postgres init. Bootstrap is owned by the `init` service (D11); there are no setup scripts.
- Package management: `uv` workspace for Python (root `uv.lock` committed, `uv sync --frozen` in Docker, base image `python:3.15-slim`), Bun workspaces for web (root `bun.lock` committed, `bun install --frozen-lockfile` in Docker, base image `oven/bun`).

Why: Manim is Python, so the worker is Python; FastAPI keeps API and worker in one package. React + MUI gives a mature component library for forms, tables, dialogs, and a persistent drawer for the tutor; Bun removes Vite, Node-for-the-frontend, npm, and Jest from the web toolchain with one runtime that bundles, serves, and tests. Strands gives the agent loop, structured output, tools, hooks, and streaming without tying BrainBench to a vendor API, because its `Model` interface is pluggable. Anatomy was chosen by the owner for figures; it replaces a Blender pipeline and yields interactive HTML instead of static renders. Alternatives considered: Remix 3 (not React, in flux), Next.js (heavier than a self-hosted SPA needs), hand-rolled agent loop, LangGraph (heavier, less direct custom-model story), Blender headless (static output, no interactivity, large image).

### D2. Provider layer modeled on omp (`packages/providers`)
omp's shape, transposed to Python. Five parts, each a module with one job:

1. **Registry** (`registry.py`, data in `registry/*.yaml`): per provider `id`, `name`, `api` (wire protocol), `base_url`, `login` (`kind: oauth-code | device-code`, `authorize_url`, `token_url`, `client_id`, `scopes`, `callback_port`, `paste_code: bool`, `device_url`), `refresh` (`token_url`, `skew_s`), `identity` (`org_scoped: bool`, `userinfo` source), `usage` (endpoint and window names, optional), `models[]` (`id`, `name`, `context_window`, `max_output`, `reasoning`, default flag). Shipped entries: `anthropic` (oauth-code, PKCE, callback port 54545, paste-code fallback, `anthropic-messages`) and `openai-codex` (oauth-code with PKCE on port 1455 plus device-code, `openai-responses` against the ChatGPT backend). Settings can disable a provider; `models.yaml` under `$BRAINBENCH_DATA` can add custom entries later with the same grammar.
2. **Vault** (`vault.py`): table `provider_credentials(id, provider, identity_key, identity jsonb, access_enc, refresh_enc, expires_at, version, disabled_at, disabled_cause, priority, created_at, updated_at)`. Token columns are AES-256-GCM encrypted with a key from `$BRAINBENCH_DATA/vault.key` (created `0600` on first run). Refresh tokens are write-only from the API's point of view; no endpoint returns them, and the SQLAlchemy model's `__repr__` omits them. Identity key follows omp (`email:<e>|org:<id>` when org-scoped).
3. **OAuth engines** (`oauth/code.py`, `oauth/device.py`): `start()` returns `{login_id, authorize_url, expires_at, callback_listening: bool}`. The code engine generates PKCE verifier and state and always leaves `complete(login_id, redirect_or_code)` available (paste path, verified against state). It additionally binds a one-shot listener on the provider's callback port when `BRAINBENCH_OAUTH_CALLBACKS=1` (the compose default publishes `127.0.0.1:54545` and `127.0.0.1:1455` from the `api` container, so a browser on the Docker host reaches it; a remote browser cannot, and the UI says so). Whichever path completes first wins; the other is closed and a late callback for a consumed state is ignored. The device engine polls at the provider's interval until approval or expiry. Pending logins live in memory with a 10-minute TTL. After token exchange the engine fetches identity (userinfo or token claims) and upserts the credential.
4. **Refresher and selection** (`refresher.py`, `select.py`): a background task every 60 s refreshes credentials within 5 minutes of expiry, single-flight per credential, compare-and-set on `version`. `invalid_grant` or revoked → `disabled_cause = needs-reauthentication` on that version only; network errors → retry next sweep. `select(provider) -> Credential` skips disabled and blocked credentials, then prefers most remaining in the tightest usage window, then `priority`. Blocks live in `provider_blocks(credential_id, scope, until, reason)`.
5. **Usage** (`usage.py`): per-provider fetchers for usage windows (Anthropic OAuth usage endpoint; Codex rate-limit headers and windows), cached 5 minutes with ±25 % jitter like omp; 429 responses write a block with the reset time; every call records `provider_usage(credential_id, model, task_class, input_tokens, output_tokens, at)`.

**Transports** (`transports/anthropic_messages.py`, `transports/openai_responses.py`) take a `Credential` and a `ModelSpec` and expose `stream(messages, tools, system, ...) -> AsyncIterator[WireEvent]` plus `structured(...)` where the protocol supports it (Anthropic tool-forced JSON, Responses `text.format` json_schema). They send the headers each subscription backend expects (Anthropic beta/oauth headers; ChatGPT backend `chatgpt-account-id` and session headers), refresh-on-401 once via the vault, and raise `ProviderRateLimited(reset_at, scope)` on 429.

**Strands adapters** (`strands_models.py`): `AnthropicOAuthModel(Model)` and `CodexOAuthModel(Model)` wrap a transport and translate wire events to Strands `StreamEvent`s with native `toolUse` blocks and `metadata` usage; `structured_output()` uses the transport's structured mode. `ProviderRateLimited` maps to `ModelThrottledException`; the job layer converts that to `ProviderLimitReached(reset_at)` for deferral.

Why: this mirrors a layer that is proven at scale in omp (registry, vault, refresher, selection, usage, transports) while staying small enough for one instance. Native tool use and streaming remove the prompted-envelope hack a CLI relay needed. Alternatives considered: delegating to the vendor CLIs (previous design; no streaming, no native tools, Node and CLIs in the image, policy only marginally safer); an API-key design (rejected by owner); Strands' built-in providers (API-key only).

### D3. Login UX
Providers page lists registry providers with status per account (`connected`, `needs-reauthentication`, `locked`, `blocked until <t>`). "Connect" calls `POST /providers/{id}/logins` and renders the engine's response: a button opening `authorize_url` in a new tab, the paste-redirect field always visible, and, when `callback_listening` is true, a "listening for callback on localhost:<port>" indicator with the note that it only works for a browser on the Docker host; device-code renders the code and polls `GET /providers/logins/{login_id}` until done. The listener binds `0.0.0.0:<callback_port>` inside the `api` container (a container-loopback bind would be unreachable through the published port) and compose publishes it as `127.0.0.1:<port>:<port>` so only the host's loopback reaches it. Disconnect calls `DELETE /providers/accounts/{id}` which revokes where supported and deletes the row. The README states, next to the Connect instructions, that subscription OAuth from a third-party app is outside Anthropic's permitted use and that the engineer's account bears that risk.

### D4. Jobs on Postgres, no broker
Table `jobs(id, type, status, payload jsonb, attempt, max_attempts, run_after, locked_by, locked_at, heartbeat_at, progress, error, provider, model, usage jsonb, checkpoint jsonb, ...)`. Workers claim with `SELECT ... FOR UPDATE SKIP LOCKED` respecting per-instance and per-type concurrency, heartbeat every 15 s, and a reaper requeues jobs whose heartbeat is older than 2 minutes. Retries: exponential backoff from 30 s, max 3 attempts, `PermanentJobError` short-circuits. `ProviderLimitReached(reset_at)` is a third outcome, distinct from failure: the handler's current checkpoint is saved to `checkpoint`, status returns to `queued`, `run_after = reset_at + jitter(0..60 s)` (or now + 5 min when the provider gave no reset), `attempt` is untouched, and `progress` reads "waiting for provider limit reset". Handlers for curation and generation resume from `checkpoint` (completed step outputs) instead of restarting. Events are written to `job_events` and pushed to the UI over Server-Sent Events via Postgres `LISTEN/NOTIFY`.

Why: one fewer service than Redis/Celery; volumes are tiny (tens of jobs per day). Alternative: `arq`/Redis rejected for operational weight on a self-host box.

### D5. Ingestion and local embeddings
- Extraction: `trafilatura` for URLs, `pymupdf` for PDFs, `git clone --depth 1` plus a file-type allowlist for repos, raw text for notes. Chunking: sentence-aware splitter targeting 1500 chars, hard cap 2000.
- Embeddings: `fastembed` with `BAAI/bge-small-en-v1.5` (ONNX, CPU, 384 dims) stored in a `vector(384)` column with an HNSW index (pgvector). Model files are cached in `$BRAINBENCH_DATA/models` on first run.
- Semantic query: cosine distance, top-k.

Why: no external API available under the no-key constraint; bge-small is fast on CPU and adequate for retrieval over an individual's corpus. Alternative: Ollama embeddings rejected to avoid a second model runtime.

### D6. Curation pipeline (job type `curation`)
Steps, each a Strands agent call with a Pydantic output model (`agent.structured_output`), orchestrated deterministically by the `curation` job handler (no LLM decides the pipeline shape):
1. `topic_extraction`: per source, map over chunk windows (about 12k chars) to emit candidate topics with chunk citations; reduce by embedding similarity (cosine > 0.85) and one merge completion for collisions.
2. `reconcile` (deterministic): each candidate is matched against existing `topics` by normalized title (casefold, whitespace and punctuation collapsed) or by embedding cosine ≥ 0.85 against the current revision's title + summary; a match reuses `topic_id` and creates a `topic_revisions` row only if title or summary differ; no match creates a topic with revision 1. Candidate chunk citations are unioned into `topic_chunks`.
3. `scoring`: batch of up to 20 topics per call with the profile; output `relevance`, `serves_targets[]`, `rationale`, `already_held`.
4. `prerequisites`: single call over the kept topic titles and summaries emitting edges with confidence; cycles are broken by dropping the lowest-confidence edge, logged.
5. `planning`: deterministic code, not LLM: topological sort, tie-break by target priority then relevance, pack into weekly blocks by the time budget; a topic whose estimate exceeds the weekly budget gets its own block spanning `ceil(estimate / budget)` consecutive weeks and the flag `exceeds_weekly_budget`. Study-time estimates come from step 3.

Topic identity: `topics(id, merged_into)` is the stable entity; `topic_revisions(id, topic_id, revision, title, summary, created_by: run|edit, created_at)` holds content; `plan_items` reference `(topic_id, topic_revision_id)` so an old plan renders the text it was built with. Sessions, assets, and tutor threads reference `topic_id`. Plan-level edits of title or summary create a new revision and a new plan version; removing or reordering only creates a new plan version. Manual merge sets `merged_into` on the loser, re-points its sessions, assets, threads, and chunk citations to the survivor, and `GET /topics/{loser}` answers with a redirect to the survivor.

Plans are immutable rows (`study_plans` with `version`); edits copy forward. Run metadata (`profile_version`, `source_ids`, `threshold`, models, step log) lives on `curation_runs`.

Progress feedback (learning-progress spec) is implemented in step 3 by injecting session history and in step 5 by moving mastered topics after unmastered ones unless they are prerequisites.

### D7. Visual generation pipeline (job types `video`, `figure`)
1. `storyboard`: for both formats, a Strands agent with the `search_chunks` tool produces the storyboard (ordered scenes with objective, narration in the profile's language, visual description, chunk citations), respecting depth preference. Stored in `storyboards` and attached to the asset.
   - For `figure`, a second structured step `figure_brief` takes the storyboard and the cited chunks and emits `applicable: bool`, `rationale`, the object or mechanism that embodies the concept, its true numbers (sizes, counts, rates, thresholds), what moves, the readout, and theme; `applicable == false` short-circuits to `skipped`. The brief is stored with the storyboard; both are provenance on the asset.
2. Video: `script` structured output whose single field is the full Manim Python file. The template fixes the contract: exactly one class `Lesson(Scene)`, whose `construct()` calls `self.next_section(name=<scene-id>)` at the start of every storyboard scene in order. Rendered in a sandbox container:
   - `docker run --rm --network none --cpus 2 --memory 4g --pids-limit 256 --read-only --tmpfs /tmp -v <host job work dir>:/work:ro -v <host job out dir>:/out brainbench/manim manim -qm --save_sections --media_dir /out -o lesson.mp4 /work/scene.py Lesson` with a wall-clock timeout (default 15 minutes). `--media_dir /out` is the only writable path (Manim writes video, partial movie cache, and `sections/` under it); `-o` names the file, not the directory. Manim derives every output name from the `-o` stem, so the final MP4 is `/out/videos/scene/720p30/lesson.mp4` and `--save_sections` writes `/out/videos/scene/720p30/sections/lesson.json` (lowercase, from the stem, not from the class name) plus one clip per section. Task 1.4 pins the Manim version and asserts these exact paths.
   - Captions: the worker reads `sections/lesson.json`, runs `ffprobe` on each section clip for its real duration, and writes one WebVTT cue per storyboard scene with the narration text spanning that section's time range; sections the script omitted get no cue and are reported in the job log.
   - On failure, the `script_repair` agent gets the script, the storyboard, and a `read_render_log` tool over the sandbox stderr; up to 3 attempts total.
3. Figure: a Strands agent session, `make_figure_agent(model, workspace)`, whose system prompt is the vendored `SKILL.md` plus the brief, and whose tools are BrainBench-owned and workspace-confined: `read_file(path)`, `write_file(path, content)`, `list_files()`, `read_reference(name)` (the skill's `references/*.md`), and `run_node(args)`. Every path is resolved and must stay under `$BRAINBENCH_DATA/jobs/<job-id>/`; `run_node` executes `node` inside the `brainbench/anatomy` sandbox image (`--network none`, CPU/memory limits, workspace mounted read-write, the vendored `kit/` and `scripts/` mounted read-only at `/skill`, `CHROME_PATH` set) with a per-call timeout, returning stdout/stderr and any PNG the skill's `capture.mjs` wrote so the agent can look at its own work as the skill demands. The session is bounded by a turn budget (default 60) and a wall-clock limit (default 30 minutes); on exit the job collects the standalone HTML, PNG preview, and build source, and fails with the transcript tail when no figure exists.
4. Assets are stored under `$BRAINBENCH_DATA/assets/<topic>/<asset-id>/` and served by the API through the Bun proxy (range support for video). Figure HTML is served from a dedicated path with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:` and embedded on the topic page in `<iframe sandbox="allow-scripts" referrerpolicy="no-referrer">`, so figure scripts cannot reach the app origin or cookies; a full-screen link opens the same URL.

Sandbox mounts: the worker launches sibling containers through the host Docker socket, and the daemon resolves bind sources on the host, not inside the worker. `BRAINBENCH_DATA` is therefore a host bind mount (compose `./data:/data`, relative to the compose file), never an anonymous named volume. At start the worker inspects its own container (`GET /containers/{hostname}/json` on the mounted socket) and reads the `Mounts[].Source` of `/data` to learn the host path; `BRAINBENCH_DATA_HOST` is only an override for when inspection fails, and the worker exits with that variable named if neither works. It translates `jobs/<id>/work`, `jobs/<id>/out`, and `skills/anatomy` to host paths when building `-v` arguments. Only those three directories are ever mounted into a sandbox; `vault.key`, `assets`, `models`, and the Postgres data are never visible to a sandbox. A startup probe writes a marker under `/data/jobs/.probe` and runs a throwaway sandbox that must read it through the resolved host path; failure stops the worker with a clear message.

Budget: `render_minutes_month` and `generation_jobs_day` counters in `usage_counters`, checked at enqueue and at claim.

### D8. Data model (Postgres)
`settings` (singleton, provider routing, enabled providers, budgets), `profiles` (singleton, `version`), `current_skills`, `target_skills`, `sources`, `chunks` (with `embedding vector(384)`, `sentence_continuation bool`), `curation_runs`, `topics` (`id`, `merged_into`), `topic_revisions` (`topic_id`, `revision`, `title`, `summary`, `created_by`), `topic_chunks`, `study_plans`, `plan_items` (`topic_id`, `topic_revision_id`, position, week_start, week_span, `exceeds_weekly_budget`, prerequisites jsonb, manually_included), `storyboards` (with optional `figure_brief jsonb`), `assets`, `study_sessions`, `jobs` (with `checkpoint jsonb`), `job_events`, `usage_counters`, `provider_credentials` (encrypted tokens, identity, version, disabled cause, priority), `provider_blocks` (credential, scope, until, reason), `provider_usage_windows` (credential, window, used_pct, resets_at, fetched_at), `provider_usage` (credential, model, task class, tokens, at), `tutor_threads` (context_type, context_id, created_at), `tutor_messages` (thread_id, role, content, citations jsonb, stopped bool, usage jsonb).

### D9. Instance access
Single engineer; the web UI is protected by an instance password set in the first-run wizard (shown whenever no password hash exists), stored as an argon2 hash in `settings`. The API issues an `HttpOnly` signed session cookie; because the Bun server proxies `/api` on the same origin, the browser sends it automatically and the SPA holds no auth state beyond "last response was 401, go to login". This is not multi-user auth; it only keeps a LAN-exposed instance private. No environment variable sets the password.

### D10. Tutor agent (sidebar)
- One Strands `Agent` factory `make_tutor_agent(model, context)` with tools `search_chunks` (scoped to the context topic first, then all sources), `get_topic`, `get_plan_summary`, `get_profile`. The system prompt carries the profile (skills, depth, language), the context description, and the citation contract: every claim from material cites `[source-title, location]`; when retrieval returns nothing relevant, say so first.
- Threads: `GET/POST /tutor/threads?context=topic:<id>|plan|general`, `GET /tutor/threads/{id}/messages`, `POST /tutor/threads/{id}/messages` returns an SSE stream (`delta`, `citation`, `related_topic`, `done`, `error`, `limit`). `POST /tutor/threads/{id}/stop` sets a cancel flag; the transport's request is aborted and the partial reply is persisted with `stopped = true`.
- Streaming: the Strands adapter yields `contentBlockDelta` events straight from the provider's SSE; the agent callback forwards them to the API's SSE generator. Native streaming on both shipped providers.
- Context switching is a client concern: the sidebar derives `context` from the route and fetches or creates the matching thread; threads persist per context.
- Concurrency: tutor calls hold a dedicated semaphore (1 in flight) separate from the job concurrency caps; they are not jobs because they are interactive, but they record `provider_usage` the same way via the hook.
- Related topics: after the reply, a cheap deterministic step embeds the reply and returns plan topics within cosine 0.8, which the UI renders as links; no second LLM call.

### D11. Zero-config bootstrap: `docker compose up` is the whole install
The root `docker-compose.yml` is the product's installer. Services and their roles:
- `db`: `pgvector/pgvector:pg16`, named volume for Postgres data, healthcheck `pg_isready`.
- `init` (from `Dockerfile.app`, `restart: "no"`, `depends_on: db: condition: service_healthy`): runs once per `up`, idempotently, in this order: (1) `alembic upgrade head`; (2) create `/data/{jobs,assets,models,skills}`; (3) vault key: if `settings.vault_fingerprint` is null (fresh vault state) generate `/data/vault.key` (`0600`) and store its SHA-256 fingerprint; if a fingerprint exists and the key is missing or its fingerprint differs, do nothing and leave the vault `locked` (the API shows recovery options; `POST /providers/vault/reset` with explicit confirmation deletes all credentials and regenerates key and fingerprint); (4) skill: read the pinned commit from `infra/anatomy.pin`; if `/data/skills/anatomy/.commit` equals it, leave it; otherwise clone into `/data/skills/anatomy.staging`, verify `git rev-parse HEAD` equals the pin, write `.commit`, and swap with a single rename (`anatomy` → `anatomy.old`, `staging` → `anatomy`, then delete `anatomy.old`); any failure leaves the installed skill untouched and logs it; (5) pre-download the embedding model into `/data/models` if absent. Needs network for the clone and model download on first run or pin change; otherwise offline-safe.
- `sandbox-manim` and `sandbox-anatomy`: build-only services (`image: brainbench/manim`, `build: infra/Dockerfile.manim`, `command: ["true"]`, `restart: "no"`). Their only purpose is that `docker compose up` builds the images on the host daemon so the worker can `docker run` them as siblings; they exit 0 immediately. `image:` names are fixed so the worker's `docker run` references resolve.
- `api` (`Dockerfile.app`, `depends_on: db: service_healthy, init: service_completed_successfully`): `uvicorn`, publishes `127.0.0.1:54545` and `127.0.0.1:1455` for OAuth callbacks, healthcheck on `/api/health`. The API does not run migrations; it refuses to serve if the schema revision is not the head it was built with.
- `worker` (`Dockerfile.app`, `depends_on: api healthy, sandbox-* completed`): mounts `/var/run/docker.sock`, resolves the host data path by self-inspection (D7), runs the sandbox probe, exits if the schema revision is newer than its migrations.
- `web` (`Dockerfile.web`, `depends_on: api healthy`): publishes `${BRAINBENCH_BIND:-127.0.0.1}:${BRAINBENCH_PORT:-3000}:3000`; on start it polls `/api/health` through its proxy and then logs `BrainBench ready at http://localhost:${BRAINBENCH_PORT:-3000}` (the host part is `localhost` unless `BRAINBENCH_PUBLIC_URL` is set, used for LAN deployments).
- Data: `./data` next to the compose file is the only host-side state besides the Postgres volume; `.gitignore` excludes it. Backup is "copy `./data` and dump Postgres".
- Builds use the repository root as context (`build.context: .`) so workspace packages are visible. `docker compose up --build` is the upgrade command after `git pull`.

Why: every manual prerequisite that existed in earlier drafts (data path variable, vendoring script, sandbox image builds, password env) is something a first-time self-hoster would get wrong; moving them into `init` and build-only services makes the compose file the single source of truth and keeps `docker compose up` honest. Alternatives considered: a `just install` wrapper (one more tool to install first); publishing prebuilt images to a registry (planned later as an optional `pull_policy`, but building locally keeps a fresh clone self-contained and avoids registry drift for sandbox images).

## Risks / Trade-offs

- [Provider policy enforcement: Anthropic or OpenAI may revoke, rate-limit, or suspend accounts used through third-party OAuth clients] → the risk sits with the engineer's own account and is stated in the README and on the providers page; each provider can be disabled; the provider layer is isolated behind the registry and transports so a provider can be replaced by an API-key or local entry without touching agents; nothing in BrainBench depends on both providers being available.
- [Provider OAuth endpoints, client ids, or backend headers change without notice (they are undocumented)] → the registry is data, transports are one file per wire protocol, and contract tests replay recorded exchanges; a providers-page "last successful probe" timestamp and a `needs-reauthentication` state make breakage visible instead of silent.
- [Anatomy sessions are slow and tool-heavy, so cost and duration vary widely] → figure jobs for a whole plan require an explicit confirmation that shows the job count; each is capped by turn budget and 30 minutes, figure sessions run 1 at a time, and every figure counts against the daily generation cap; the brief is pre-computed by the storyboard agent so the session starts with true numbers.
- [Figure HTML is agent-generated and executes scripts in the engineer's browser] → served under a sandboxing CSP and embedded with `<iframe sandbox="allow-scripts">` only (no `allow-same-origin`), so it cannot read cookies, storage, or call the API as the engineer.
- [Anatomy upstream changes its workflow or file layout] → vendored at a pinned commit recorded in `infra/anatomy.pin`; the collector looks for standalone HTML and PNG by content, not by fixed file names; an update is a pin change that `init` applies as a staged, verified, atomic swap on the next `docker compose up --build`.
- [Strands `Model` interface evolves (it is a young SDK)] → pin `strands-agents`; `strands_models.py` is the only file touching the interface; transports are independent of Strands and testable alone.
- [Bun's fullstack server or HTML-import bundling regresses on upgrade] → pin the Bun version in `package.json` `engines` and `.bun-version`; the SPA is plain React so a fallback to `bun build` static output behind nginx is a config change only.
- [Python 3.15 is two days old; binary wheels for `onnxruntime` (fastembed), `pymupdf`, `asyncpg`, or `pydantic-core` may not yet publish cp315 builds] → the compatibility gate is an install-and-import smoke in the target image, not `uv lock` alone: CI builds `Dockerfile.app` with `PYTHON_VERSION=3.15` and runs `python -c "import app.main, app.worker"` plus the unit suite inside it. If that fails for a dependency with no cp315 wheel and no quick source build, the fallback is one documented change set: `.python-version` → `3.14`, `requires-python = ">=3.14"`, `PYTHON_VERSION` build arg and base image → `3.14-slim`, `uv lock` regenerated, CI matrix switched, and every `lazy import` rewritten to the `__lazy_modules__` form (3.14 cannot parse the keyword). Nothing else changes.
- [Subscription rate limits stall curation of large corpora] → batch sizes in D6 keep calls bounded; jobs defer until the reported reset instead of failing; the UI shows the limit state.
- [Generated scripts are untrusted code] → network-less, read-only, resource-capped containers; outputs limited to the mounted `/out`.
- [Manim renders slow on CPU] → medium quality (`-qm`) default, per-topic rather than per-plan generation by default, concurrency 1 for renders.
- [Local embedding quality on non-English material] → model is configurable; `bge-m3` as a documented alternative at higher CPU cost.
- [Vault key loss makes every stored account unusable] → `vault.key` lives in `$BRAINBENCH_DATA`, documented backup/restore; the providers page shows "locked" with the path instead of failing silently; re-connecting providers restores service without data loss elsewhere.

## Migration Plan

Greenfield: `docker compose up` builds everything, bootstraps the data directory and the schema through `init`, and announces the URL. Upgrade: `git pull && docker compose up --build`; `init` migrates before the API starts. Rollback is a documented three-step sequence because the older release does not carry the newer revision files: (1) `docker compose stop web worker api`; (2) with the current release still checked out, `docker compose run --rm init alembic downgrade <previous-release-revision>` (each release records its head revision in `infra/schema.rev`, so the target is read from the previous tag); (3) check out the previous tag and `docker compose up --build`. Every migration ships a working `downgrade()`, and task 10.2 exercises this sequence. The alternative rollback is restoring `./data` and a Postgres dump from backup. Removing an instance is `docker compose down -v` plus deleting `./data`.
